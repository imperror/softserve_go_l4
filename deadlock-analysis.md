# Аналіз дедлоку (Частина 2)

## Код, що аналізується

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	ch := make(chan int) // небуферизований канал

	wg.Add(1)
	go func() {
		// симуляція важкої роботи
		ch <- 42
		wg.Done()
	}()

	wg.Wait()
	fmt.Println(<-ch)
}
```

### Відповідь ШІ

**TL;DR:** жодної гонки (data race) тут немає — це **circular wait**
(циклічне очікування), і він відтворюється 100% детерміновано.
`wg.Wait()` і `ch <- 42` чекають один на одного.

Відтворено буквально (go1.27.3, darwin/arm64, вивід самої програми):

```
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [sync.WaitGroup.Wait]:
  sync.runtime_SemacquireWaitGroup(...)   sema.go:114
  sync.(*WaitGroup).Wait(...)             waitgroup.go:206
  main.main()                             main.go:19   <- wg.Wait()

goroutine 19 [chan send]:
  main.main.func1()                       main.go:15   <- ch <- 42
  created by main.main in goroutine 1       main.go:13
```

Два теги стану — `[sync.WaitGroup.Wait]` і `[chan send]` — це і є весь
дедлок, який надрукував runtime.

#### Покрокова послідовність переплетення

| #   | Хто     | Інструкція                | Що відбувається в runtime |
|-----|---------|---------------------------|---------------------------|
| 1   | main    | `make(chan int)`          | створено `hchan`: `buf = nil`, `qcount = 0`, `sendq = nil`, `recvq = nil` |
| 2   | main    | `wg.Add(1)`               | лічильник WaitGroup: `0 -> 1` |
| 3   | main    | `go func(){…}()`          | горутина 19 стає *runnable*; main **продовжує виконуватись** — `go` не блокує, і планувальник нічого не гарантує щодо того, хто першим вийде на CPU |
| 4a  | 19      | `ch <- 42`                | `recvq` порожній → `gopark(&c.sendq, …, waitReasonChanSendNilReceiver)`. Значення **42 не копіюється нікуди**, воно лишається у фреймі відправника. Горутина 19 = `_Gwaiting [chan send]` |
| 4b  | 1       | `wg.Wait()`               | лічильник = 1, тому `counter() > 0` → `sema.acquire(&w.sema)`. Горутина 1 = `_Gwaiting [sync.WaitGroup.Wait]`, знята з run queue |
| 5   | —       | —                         | `ch <- 42` не повернула керування, отже наступна інструкція горутини 19 — `wg.Done()` — **навіть не є кандидатом на виконання**. Лічильник досі 1 |
| 6   | main    | `fmt.Println(<-ch)`       | **недосяжний рядок**: керування ніколи не повертається з рядка 19 |
| 7   | runtime | `checkdead()`             | усі горутини в `_Gwaiting`, жодної runnable, усі `M` в очікуванні → `throw("all goroutines are asleep - deadlock!")`, exit code 2, `42` не надруковано |

Головний механічний момент: **небуферизований канал не має проміжного
сховища**. Надсилання у канал з `cap == 0` — це не «скопіювати в буфер
і повернутись», а *rendezvous*: значення передається напряму зі стека
відправника в стек отримувача. Якщо в `recvq` ніхто не чекає, у
`sendq` паркується сам відправник. Тобто рядок `ch <- 42` за семантикою
— **блокуюча точка синхронізації**, а не «відправив і забув».

#### Чому `wg.Wait()` перед читанням зупиняє виконання

`wg.Wait()` — це не «зачекати на мить», а «приспати цю горутину, доки
лічильник не стане 0», і єдина подія, що робить його 0, — це `Done()` з
іншої горутини. Маємо замкнений цикл залежностей:

```
main ──wg.Wait() чекає на──▶ wg.Done() ──виконується після──▶ ch <- 42
▲                                                                    │
└──────◀── <-ch — єдиний такий рядок, він у main ПІСЛЯ wg.Wait()─────┘
```

Нижнє ребро іде справа наліво: саме `ch <- 42` блокується, чекаючи на
читання, яке мало б статися в `main`. Усі три ребра — **AND**-ребра, і
розірвати цикл може тільки `main`, але `main` приспаний. `Done()` —
це код, який під час виконання програми стає недосяжним:
наступні інструкції горутини не можуть виконатись, поки попередня
інструкція цієї ж горутини припаркована. Це не залежить від `GOMAXPROCS`:
при 1 ядрі й при 64 результат однаковий, бо проблема не «немає CPU», а
«немає runnable горутин».

Дві деталі, які варто закріпити:

- **`wg.Add(1)` і сам лічильник — не причина.** Причина — *порядок*:
  «чекати, поки відправник завершиться» поєднано з «відправник
  завершується лише тоді, коли з каналу прочитали».
- **Детектор дедлоків у Go — «fair-weather friend».** Він спрацьовує,
  лише коли весь процес стоїть. Перевірено варіант із додатковою
  `time.Sleep`-горутиною: runtime **мовчав** усі 3 с (живий таймер =
  «раптом щось прокинеться»), надрукував фоновий рядок і лише потім
  видав `fatal error`. У сервері чи в тесті з таймерами такий дедлок
  висить **вічно без жодного повідомлення** — саме тому
  `deadlock/fixed_test.go` обгортає `Run()` у
  `select { case …: case <-time.After(2 * time.Second) }`, а не покладається
  на детектор.

#### Варіанти виправлення (усі чотири перевірено — код друкує `42`, exit 0)

```go
// v1 — читаємо ПЕРШИМ, потім Wait. Мінімальний diff, WaitGroup лишається чесним.
go func() { defer wg.Done(); ch <- 42 }()
fmt.Println(<-ch)
wg.Wait()

// v2 — робимо надсилання неблокуючим: буфер cap 1 зберігає 42, send
// повертається, Done() виконується, Wait() повертається, main читає з буфера.
ch := make(chan int, 1)
go func() { defer wg.Done(); ch <- 42 }()
wg.Wait()
fmt.Println(<-ch)

// v3 — ідіоматично для одного значення: прибрати WaitGroup взагалі.
// Сам receive і є happens-before edge (Go memory model: "send happens
// before receive completes"), чекати більше ні на що.
ch := make(chan int)
go func() { ch <- 42 }()
fmt.Println(<-ch)

// v4 — wg.Done() ПЕРЕД надсиланням: працює, але випадково.
go func() { wg.Done(); ch <- 42 }()
wg.Wait()
fmt.Println(<-ch) // друкуює 42, але WaitGroup більше не доводить, що send сталося
```

**Правило, яке варто запам'ятати:** ніколи не давайте сигналу про
завершення, на який чекає `Wait()`, залежати від rendezvous, який має
виконати той самий, хто й чекає. Або нехай канал виконує синхронізацію
(v3), або буферизуйте (v2), або читайте до `wg.Wait()` (v1) — і завжди
`defer wg.Done()`, щоб лічильник не «тек» на достроковому `return` чи
паніці.

## Мінімальне виправлення

Робочу, тестовану версію виправлення реалізовано в
[`deadlock/fixed.go`](./deadlock/fixed.go) (функція `Run`), а
автоматична перевірка — у `deadlock/fixed_test.go`. Коротко опишіть
своїми словами, яку зміну порядку операцій (чи структури каналу) ви
застосували і чому саме вона усуває циклічне очікування.

Виправлення — це варіант **v3** з відповіді ШІ: змінюємо лише *порядок*
операцій, а не логіку. Горутину, що надсилає `42`, запускаємо після
створення небуферизованого каналу, а `sync.WaitGroup` прибираємо зовсім,
бо для одного значення він надлишковий: сам `<-ch` уже є точкою
синхронізації й за Go memory model гарантує, що `ch <- 42` сталася раніше.
Читання `<-ch` стоїть *до* будь-якого очікування, тому воно миттєво
знімає відправника з `sendq` — ланцюг «Wait → Done → send → receive →
Wait» розмикається одним rendezvous. Альтернативи без пастки WaitGroup:
`make(chan int, 1)` (send повертається в буфер) або прочитати канал до
`wg.Wait()`. Перевірено: `go test -race -count=3 ./deadlock/...` — 100%
покриття, а 5000 викликів `Run()` не призводять до витоку горутин
(`runtime.NumGoroutine`: 2 → 2).
