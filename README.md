# Домашнє завдання · Урок 4 (Конкурентність у Go, Go + GenAI)

Цей репозиторій — готовий каркас для домашньої роботи. Частина завдань
перевіряється **автоматично** через GitHub Actions при кожному пуші чи
Pull Request — запуште код у гілку `main` або відкрийте PR і перевірте
вкладку **Actions**.

**Загальний орієнтовний час:** до 2 годин.

## Частина 1 — Побудова синхронного конвеєра вручну (40 хв)

**Перевіряється автоматично тестами `pipeline/pipeline_test.go`.**

⚠️ **Не використовуйте ШІ для цієї частини** — весь код пишіть
самостійно, у своєму редакторі.

Реалізуйте у `pipeline/pipeline.go` простий послідовний конвеєр
обробки даних за моделлю CSP:

1. **Generator** — `Generate(n int) <-chan int`: горутина генерує
   рівно `n` випадкових цілих чисел у діапазоні `[1, 100]` і надсилає
   їх у канал. Після `n`-го числа канал закривається.
2. **Filter** — `Filter(in <-chan int) <-chan int`: горутина читає з
   `in`, пропускає лише парні числа, закриває вихідний канал, коли
   `in` вичерпано.
3. **main()** (уже реалізовано в `cmd/pipeline/main.go`) — читає з
   фінального каналу і друкує результати.

### Вимоги

- Використовуйте **спрямовані типи каналів** (`chan<-` і `<-chan`) у
  сигнатурах функцій — це вже закладено в заглушках, не змінюйте
  сигнатури.
- Запустіть програму з детектором гонок і переконайтеся, що він
  показує нуль гонок:

  ```bash
  go run -race ./cmd/pipeline
  ```

Запустити тести локально:

```bash
go test -race ./pipeline/... -v -cover
```

## Частина 2 — Промпт-інжиніринг: аналіз дедлоку (40 хв)

**Перевіряється частково автоматично**: тести `deadlock/fixed_test.go`
для практичної частини, і перевірка заповнення `deadlock-analysis.md`.

Дано код, що гарантовано зависає:

```go
var wg sync.WaitGroup
ch := make(chan int) // небуферизований канал

wg.Add(1)
go func() {
    ch <- 42
    wg.Done()
}()

wg.Wait()
fmt.Println(<-ch)
```

### Завдання

1. Розробіть промпт для ШІ-асистента, який просить **не просто
   переписати код**, а пояснити точну послідовність переплетення
   горутин, що веде до зависання — чому `wg.Wait()` перед читанням з
   небуферизованого каналу зупиняє виконання.
2. Надішліть промпт своєму ШІ-асистенту, проаналізуйте відповідь.
3. Збережіть промпт і пояснення ШІ у [`deadlock-analysis.md`](./deadlock-analysis.md)
   (інструкції щодо структури — у самому файлі).
4. **Практичне застосування:** реалізуйте виправлену версію в
   `deadlock/fixed.go` (функція `Run`) так, щоб вона повертала `42`
   без дедлоку.

Запустити тести локально:

```bash
go test -race ./deadlock/... -v -cover
```

> 💡 Тест `TestRun_DoesNotDeadlock` викликає `Run()` в окремій
> горутині і чекає результат із тайм-аутом 2 секунди — якщо дедлок
> ще не виправлено, тест провалиться з чітким повідомленням, а не
> зависне назавжди.

## Частина 3 — Агентна розробка: пул воркерів з тайм-аутом (40 хв)

**Перевіряється автоматично тестами `workerpool/workerpool_test.go`.**

Використовуючи ШІ-агента (GitHub Copilot, Cursor Composer чи подібний
автономний асистент), реалізуйте `workerpool/workerpool.go`:

1. Запустіть пул із **рівно 3 воркерів**, що обробляють завдання
   (симуляція конкурентного отримання розміру URL).
2. Якщо `Job.Fetch` не встигає за виділений `timeout`, воркер має
   перервати очікування через `select` + `context.WithTimeout` (чи
   `time.After`), щоб уникнути витоку пам'яті/горутин.

### Взаємодія з агентом

- Дайте агенту високорівневу інструкцію-мету (не пишіть код за нього
  рядок за рядком).
- Попросіть агента написати супровідний юніт-тест, що перевіряє
  механізм тайм-ауту (окремо від готових тестів цього репозиторію —
  наприклад, `workerpool/workerpool_ai_test.go`).
- Попросіть агента перевірити власноруч згенеровані циклі на
  відповідність правилам захоплення змінної циклу Go 1.22+.
- Виконайте фінальне рішення й тести з увімкненим детектором гонок:

  ```bash
  go test -race ./...
  ```

Запустити готові тести локально:

```bash
go test -race ./workerpool/... -v -cover
```

## Що саме перевіряє CI (GitHub Actions)

Конвеєр `.github/workflows/tests.yml` на кожен push/PR виконує повний
чекліст цього заняття, **з увімкненим детектором гонок** (`-race`) —
так, як і вимагають усі три частини завдання:

| Крок                              | Що перевіряє                                                  |
|------------------------------------|------------------------------------------------------------------|
| Перевірка структури репозиторію    | Наявні всі обов'язкові файли                                     |
| Перевірка `deadlock-analysis.md`   | TODO-заглушки замінені на реальний текст                        |
| `gofmt -l .`                       | Код відформатовано за стандартом Go                              |
| `go vet ./...`                     | Немає підозрілих конструкцій                                      |
| `go test -race ./... -v -cover`    | Уся логіка проходить тести з покриттям, **нуль гонок**            |
| `go build ./...`                   | Проєкт компілюється без помилок                                    |

**Важливо:** усі кроки перевірки виконуються **незалежно один від
одного** — якщо один крок провалюється (наприклад, незаповнений
аналіз дедлоку), решта кроків (`gofmt`, `go vet`, тести, збірка) усе
одно запускаються. Наприкінці окремий крок **«Підсумок перевірки»**
показує статус УСІХ перевірок одразу, а не лише першої помилки — щоб
ви бачили весь обсяг роботи, що залишився, за один погляд на лог.

**Ще важливо:** тести в цьому репозиторії навмисно захищені
тайм-аутами (`select` + `time.After`) саме на випадок, якщо ваша
реалізація має дедлок чи витік горутини — замість того, щоб
підвісити весь запуск CI назавжди, такий тест провалиться за кілька
секунд із чітким поясненням причини.
